## Breaking changes

- **[client-v2, jdbc-v2]** `QuerySettings#setUseTimeZone` and the `use_time_zone` / `server_time_zone` client options
  (`Client.Builder#useTimeZone`, `Client.Builder#setServerTimeZone`, JDBC connection properties) now reject an unknown
  or malformed time zone ID with an `IllegalArgumentException`. Before, `TimeZone#getTimeZone(String)` silently replaced
  such an ID with `GMT`, so date-time values were interpreted in the wrong time zone. IDs are validated with
  `ZoneId#of`, the check that `Client.Builder#build` already did for `use_time_zone` (and for `server_time_zone` when
  `use_server_time_zone` is on). Because of this, `QuerySettings#setUseTimeZone`, and `server_time_zone` set together
  with `use_time_zone`, now also reject legacy `java.util.TimeZone` IDs that `ZoneId` does not accept: three-letter
  aliases such as `PST`, `IST` or `EST`, and custom IDs such as `GMT+5:30`, `GMT+530` or `GMT+20`.
  Use a region ID (`America/Los_Angeles`) or an offset (`GMT+05:30`, `+05:30`) instead. Offsets with seconds
  (`+05:30:45`, `GMT+05:30:45`) are rejected on every Java version: on Java 17 and earlier `TimeZone` replaces them
  with `GMT`, and on later versions they are rejected too, so that a setting does not depend on the Java version
  (on Java 21, `GMT+05:30:45` was accepted before). Offset IDs with a `UTC` or `UT` prefix (`UTC+05:30`) and plain
  offsets (`+05:30`) now give their offset instead of `GMT`.
  (https://github.com/ClickHouse/clickhouse-java/issues/3286)
