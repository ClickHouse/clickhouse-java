# Release 0.12.0

# Migration Guide

## CLIENT-V2: Compressed reads fail with `DataTransferException`

This is a breaking change.

A failure while reading a native LZ4 or ZSTD response now throws
`com.clickhouse.client.api.DataTransferException`. Earlier releases threw `IOException`,
`EOFException`, or `ClientException`, depending on the API.

Catch `DataTransferException` when the connection drops, the response ends before the block is
complete, or the block header, size, checksum, or codec result is invalid.

```java
try (QueryResponse response = client.query("SELECT * FROM events").get()) {
    ClickHouseBinaryFormatReader reader = client.newBinaryFormatReader(response);
    while (reader.hasNext()) {
        reader.next();
    }
} catch (DataTransferException e) {
    // Close the response and run the query again if that is safe.
}
```

`e.getQueryId()` returns the server query ID, or the query ID from the request when the server did not return one.

The client does not retry after the response starts. Close the response and run the full query again. Rows that were already read can arrive again.

JDBC still throws `SQLException`. A nested socket timeout now uses the driver's network-timeout handling and can close the connection. A pool must not reuse a connection that the driver closed.

## CLIENT-V2, JDBC-V2: Native blocks are limited to 64 MiB

The client refuses a native compressed or uncompressed block larger than 64 MiB. This stops a bad
block header from forcing an allocation up to the 1 GiB protocol maximum.

The ClickHouse default `max_compress_block_size` is 1 MiB, so most servers need no change.

If the server sends larger blocks, set the smallest limit that still accepts them:

```java
new Client.Builder()
        .setMaxCompressionBlockSize(128 * 1024 * 1024)
        .build();
```

The property is `compression.max_block_size`. The range is 1 MiB to 1 GiB. A higher limit uses
more memory.

See [issue #3321](https://github.com/ClickHouse/clickhouse-java/issues/3321).
